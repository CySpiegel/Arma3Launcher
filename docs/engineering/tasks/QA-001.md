# QA-001 — First native checkpoint acceptance plan

This is a prospective check plan, not executed evidence or a passing review.
The lead binds a submitted immutable candidate and the current ARCH-001 adoption
before review. The implementation author cannot supply its sole QA verdict.

## Independent code and test review

Review the entire first candidate against ARCH-001 r2 and A1–A5. Prioritize:

- Read-only Steam/game handling: no addon copying, symlink creation, generated
  game-folder files, or Steam launch-settings mutation.
- VDF/config parsers treat metadata as bounded data, including malformed input,
  duplicate keys, comments, escaped strings and excessive nesting where relevant.
- Manifest readiness and game/DLC inheritance; stale library apps indexes;
  missing-manifest manual selection; explicit installation loss; deterministic
  duplicate Workshop precedence. Assertions must exercise the intended rules.
- Native argv is passed to an exact app URL without shell evaluation; spaces,
  disallowed delimiters, mixed-case advanced conflicts, already-running checks,
  returned-URL mismatch, and ambiguous handoff remain honest.
- UI work remains responsive through scans; stale/canceled scans cannot overwrite
  current data, and missing saved selections remain visible blockers.
- Configuration persistence round-trips mode/options/content order, surfaces
  errors, and cannot silently overwrite malformed or newer-version data.
- Names, signatures, module direction, error handling, formatting and file sizes
  comply with the adopted register. Check tests' assertions, not just counts.

Independent verification uses the actual canonical gate and records the exact
candidate hash, environment, command, exit code, test count and full log paths.
Run gate/build operations serially; the implementation worker must release its
mutable build outputs before independent execution.

## Native app smoke

Use the real compiled macOS app through native UI automation. No web mockup
substitutes for this check. Internal smoke may precede commit, but user inspection
must use a committed candidate with current independent gate/review evidence.

1. First launch: real discovery shows expected game modes, four Workshop items
   and observed installed DLC. Verify installed labels do not imply ownership.
2. Search by a real addon name; toggle a subset; inspect summary and source path.
   Refresh and switch list sections without losing selection or window position.
3. Create/rename/reopen a preset and verify content, mode and options. Preserve
   the user's own configurations; any disposable smoke preset is identified.
4. Exercise missing-Steam state and explicit Open Steam action. No game launch
   may be reported from that action alone.
5. Inspect useful settings/folder selection and advanced argument validation.
   Do not delete, rename or edit actual game files to induce failures; use
   synthetic tests for destructive/unavailable installation cases.
6. Verify labels, keyboard control, resizing, readable list density, and both
   app appearances. Use per-app appearance controls, not global OS changes.
7. Preserve screenshots or identify the actual tool transcript capture when a
   standalone screenshot artifact is unavailable. Bind captures to exact build
   and appearance, with no claim that generated concepts show running software.

## Real-game integration

Before Play, verify no existing Arma process would be disturbed. Use only a
session-launched game for any subsequent close action. Record requested bundle,
mode and actual process arguments; do not expose credentials/account IDs.
Load a representative addon and optional DLC from original Steam paths. Look
for positive in-game evidence. Test each advertised mode where feasible and
clearly identify anything unverified. A4 is incomplete if the game cannot show
that content loaded, even when launch handoff succeeded.

No acceptance of new EULA/terms or unexpected OS privacy/access prompts is
implied by game testing. Record an actual prompt if encountered, while continuing
independent checks. Do not install Rosetta or change Steam branches to force a pass.

## User handoff

Once a reviewable test candidate is committed and independently gate-verified,
notify the user with the built app path, exact commit, what works, and concrete
remaining test limitations. Their in-use visual/game feedback closes the
corresponding acceptance criteria; a lack of response is not approval.
